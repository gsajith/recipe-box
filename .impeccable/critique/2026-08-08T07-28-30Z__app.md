## Overall Impression

The app is now good enough that its remaining problems are all *edges* — and every one of them lives on a surface nobody has owned yet. `/`, the detail modal and the profile have each been redesigned from first principles and they show it. `/users`, `/settings`, `/onboarding`, the Add Recipe modal and the notification sheet have only ever been built, never designed.

The single biggest opportunity: **the product refuses to save a recipe when extraction fails, on the two capture surfaces people actually use** — while the best failure design in the codebase sits behind `/share-target`, which appears on zero signed-in surfaces. PRODUCT.md Principle 4 says degraded metadata is a first-class state. Two of three capture paths disagree with it.

## Priority Issues

### [P0] Extraction failure dead-ends the in-app save path
**What.** `app/api/recipes/route.ts:78` returns `error.message`; `RecipeForm` renders it verbatim — verified live as `Failed to extract recipe metadata from URL`. The clipboard banner does the same (`app/page.tsx:177-181`). The `allowFallback` "save the bare link" path is wired to exactly one caller: `app/share-target/page.tsx:70,76`.
**Why it matters.** For any site that blocks scraping, the core task — save this recipe — is impossible from the two capture surfaces reachable inside the app. The user gets a log line at the moment of highest abandonment risk, in the middle of scene 1 (saving mid-scroll). PRODUCT.md Principle 4 makes degraded metadata first-class; here the product refuses to save at all.
**Fix.** Lift `/share-target`'s error block into a shared component; pass `allowFallback: true` from `handleAddRecipe` and from the banner. Never render `error.message` — map to the human line already written at `app/share-target/page.tsx:176`.
**Suggested command:** `/impeccable harden`

### [P1] The search field displays a query the list is no longer using
**What.** `SearchBar` owns `query` in its own `useState` and accepts no `value` prop (`components/SearchBar.tsx:9-16`). `RecipeFilterPanel.tsx:277-278` calls `clearAllFilters(); handleSearch("")` — resetting the parent's state but unable to reach the child's. Verified in source and with real keystrokes: box reads the dead query, × visible, 84 cards showing.
**Why it matters.** Search "gochujang", see nothing, tap Clear, see your whole library — and now believe you have no gochujang recipes, because the box still says you're filtered. A control that misreports state is worse than no control.
**Fix.** Make `SearchBar` controlled: add `value: string`, delete the internal `useState`. Same pass should fix `RecipeFilterPanel.tsx:79`, which disables exhaustive-deps and omits `searchQuery` from the re-filter effect — the same stale-closure family.
**Suggested command:** `/impeccable harden`

### [P1] The kitchen scene's controls are under the tap floor, and Delete is 8px from Share
**What.** Detail modal at 390, measured with a 44×44 corner probe: Back **79.1×32.9**, Copy share link **38×38**, Delete **40×38**, Edit details **32×32**, Edit tags **63×32** — all 0 of 4 corners passing. Delete sits at x=334, Share at x=288: an **8px gap**, both over photography. Because `.deleteBtn` is `display: none` under `@media (hover: none)`, this 40×38 button is the *only* delete on a phone. On the expanded profile, "Collapse recipes" is **30×30** and is the only way back.
**Why it matters.** PRODUCT.md says the kitchen scene sets a floor that *exceeds* the usual minimums. Wet hands, arm's length, and a permanent-destruction button 8px from Share.
**Fix.** The codebase already contains the answer: `app/page.module.css:211` gives the 28×28 clipboard dismiss a 44×44 `::after` hit area — verified working, all four corners hit. Apply that pattern to every sub-44 control, and move Delete out of the photo overlay to a text button at the bottom of the modal, away from Share.
**Suggested command:** `/impeccable adapt`

### [P2] The notification sheet is a full-screen overlay that isn't a dialog
**What.** Measured at 390: the panel is **390×844**, but `role: null`, `aria-modal: null`, **0** `[inert]` nodes, and `window.scrollBy(0,900)` moves the page behind it. The 84 card buttons behind stay focusable. It carries `aria-label="Following feed"` (`NotificationPanel.tsx:130`), so it is named — but it does not use `lib/useModalDialog.ts`, which both other modals do (`RecipeDetail.tsx:69`, `RecipeForm.tsx:87`).
**Why it matters.** A screen-reader user opens the feed, tabs four rows, and falls silently into 84 recipes they cannot see. Same product, same gesture, opposite result from the other two overlays.
**Fix.** One line: `const dialogRef = useModalDialog<HTMLDivElement>(onClose)`. The hook already does focus-in, Escape, the Tab trap, `inert` on siblings, scroll lock on `document.scrollingElement`, and focus restore.
**Suggested command:** `/impeccable harden`

### [P2] The clipboard banner has no plausibility check and no failure state
**What.** `app/page.tsx:70` accepts any `^https?://`. Verified live: it offered to save **`http://localhost:3000/` — RecipeBox's own homepage** — with a live Save button. The preview returned 500 and, because `app/page.tsx:139-148` only acts `if (data)`, the title skeleton pulsed indefinitely. Last round it offered a Neopets auction page; same root cause, still open.
**Why it matters.** This banner is the headline mechanic of a capture-first product. Two junk offers and the user stops reading it, which kills the real ones.
**Fix.** Reject the app's own origin before offering. Treat a non-ok preview as a *state*: swap the skeleton for the bare hostname and keep Save enabled — which is precisely the degraded save PRODUCT.md asks for.
**Suggested command:** `/impeccable harden`

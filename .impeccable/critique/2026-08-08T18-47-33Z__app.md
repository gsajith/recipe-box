## Priority Issues

### [P1] A save confirmed once, then invisible
**What.** Saving under an active filter opens the new recipe's modal — good. Close it and the recipe is gone: verified with `?source=Instagram` active, `[role=status]` still read "Showing 24 of 41 recipes", the card was absent from the list, and the recipe existed (collection went 84 → 85). Filters now persist across reloads, so a stale filter is far more likely to be active than it was a week ago, and nothing in the save path knows about them.
**Why it matters.** Scene 1. Casey filtered to Blog last week, that filter is in her URL, and she saves a Reel mid-scroll. She sees it once, closes it, and her collection appears not to contain it.
**Fix.** When a save lands outside the active filters, say so and offer the way back — clear the filters, or write it into the `[role="status"]` region that already exists. → `/impeccable harden`

### [P1] The product manufactures thumbnail-less recipes and has no card for them
**What.** `components/RecipeItemContent.tsx:68` gates the whole media block on `{recipe.thumbnail_url && (...)}`, so a null thumbnail drops the cover **and** the `SourceBadge`. Measured on a real fallback save: **316×81**, no `<img>`, no badge, no placeholder, one heading.
**Why it matters.** DESIGN.md's Do list calls the oat placeholder "the shipped behavior, **and it is the common case**". Before PR #4 this card was rare; PR #4 made it routine on purpose.
**Fix.** Render the media block unconditionally; with no thumbnail, emit the oat placeholder in its non-pulsing error state and keep the badge — the origin mark is the only identity a titleless, imageless recipe has left. → `/impeccable harden`

### [P1] The feed's Save doesn't know what you already have
**What.** Feed rows render an enabled "Save" regardless of whether the recipe is already yours; the 409 is the discovery mechanism. In this account both available rows returned 409 — which is data-dependent, but the structural gap is not: nothing pre-computes a saved set.
**Why it matters.** Scene 3, and PR #5's headline social feature. You follow people whose taste you trust, which is exactly the population whose saves overlap yours. Every dead button teaches that the feed's one interactive affordance is decorative.
**Fix.** Return `already_saved` per item from `/api/feed` and render the disabled "Saved" state on first paint. The 409 handler is already correct; it just shouldn't be how you find out. → `/impeccable harden`

### [P2] "Show more" throws keyboard focus to the top of the page
**What.** After activating it, `document.activeElement` is `<body>` — the button unmounts on the last page and focus is not moved.
**Why it matters.** Sam is ejected from position 62 to position 0 of the tab order by the control whose entire job is "continue where I am". Related: the page cursor isn't in the URL while filters are, so back-navigation restored `?source=Instagram` but reset 41 cards to 24 and scroll 8,205 → 0.
**Fix.** Move focus to the first newly-rendered card, announce the new count through the existing status region, and put the page count in the query string beside the filters. → `/impeccable adapt`

### [P2] Six fields in the recipe edit panel have no accessible name
**What.** The panel does use `<label>` elements (`RecipeDetail.tsx:265–323`) — but they are siblings, carry no `htmlFor`, and the inputs have no `id`, so they contribute no accessible name. Five are named only by placeholder, which vanishes on input; **Title has no name at all**. The Recipe URL field is `type="text"` with no `inputMode`, on the same phone where Add Recipe got all four attributes.
**Why it matters.** WCAG 3.3.2 and 4.1.2, on the only path to notes. `/settings` two clicks away does it correctly with `id` + `<label for>` — the pattern exists in the repo.
**Fix.** Add `htmlFor`/`id` pairs, and `inputMode="url"` to the URL field. → `/impeccable harden`
